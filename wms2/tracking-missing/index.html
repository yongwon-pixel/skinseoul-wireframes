Unrecognized Tracking — Changes (new admin page)

  1. 0New admin page — replaces the manual process of setting orders without a tracking number aside. Coupang creates the order number instantly but generates the tracking number later → unrecognized / unentered items are collected and tracked here — F Tracking Automation
  2. 1Unrecognized product pool — aggregates physical products sent via the View Orders barcode-recognition-failure popup, highlighted in yellow. The last-mile tracking number collected at scan time is shown to the left of the order number. The order number (Coupang purchase) is mostly "–" — lookup-matched items are resolved at the registration step and never reach the pool. Each item shows brand, product name, size, barcode, quantity, and memo — F Flow 5
  3. 2Suspected orders (auto-matched) — via barcode→product comparison, candidates are shown only when an order containing this product exists and that order is in the Processing stage, multiple possible. Mostly JIT orders from non-Coupang channels such as Naver and the official mall (Coupang items are filtered out by the order-number lookup). On registration, the automatic #unrecognized-tracking notification also @mentions the suspected PICs → handlers only need to come and confirm — 2026-07-23 UX inversion
  4. 3"Review & Match" button → match modal (M1) — click a candidate product line to match (matched to a product line, not order-level). The candidate list covers every "contains the product + Processing" order, so there is no separate PIC search (if it is not here, the data is wrong — manual-search fallback removed 2026-07-23). On confirm, the tracking number is registered to that product line, the item is removed from the pool, and a comment is automatically posted to the order's Comments (@mentions the registrant "Matched to the order" → Slack notification). Row ✕ on the right now opens the removal confirm modal (M2): a mandatory reason (Registered by mistake / Routed to inbound request + Inbound No. / No action needed / Other + memo) → soft-delete with reason·actor·time recorded, a green "✓ Removed from pool" toast, and an auto-comment on the pool item — PD-5/PD-60 owner-confirmed 2026-08-03 · F Flow 2·5
  5. 4Brand name always shown at the front of Product Name (inherits View Orders decision B) — B
  6. 5Comments — top-right hub ([@ Mentions]+[★ Saved]+search across all comments · newest first). @mentions trigger automatic Slack notifications; clicking a comment opens the order page — 0. UI 1+2

2026-07-23 simplification decision: removed the per-PIC group tables, bulk-action bar, Slack-notified column, resolved log, unified search bar, and the in-page register button and modal. Registration has a single entry point — the View Orders popup — and notifications are sent automatically. Matching UX inversion: handlers searching for their own name per product (old) → the system presents suspected orders and handlers first, and handlers only confirm (new). Since candidates are the full set of "contains the product + Processing" orders, the manual-search fallback was removed as well (2026-07-23). (2026-08-03) the one-click ✕ removal was replaced by the confirm modal M2 per the owner-confirmed rule that every destructive action gets a confirm step, a reason, and a toast (PD-5/PD-60); the dead v1 CSS/JS leftovers of the 2026-07-23 simplification were also deleted (WF-10).

Flow summary: (1) View Orders barcode recognition fails → order-number lookup popup → (2a) match succeeds → the tracking number is matched and registered on the spot (never enters this list; rescanning recognizes it normally) / (2b) no order number or match fails → send-to-unrecognized modal (English product-name autocomplete · quantity · memo) → (3) automatic #unrecognized-tracking notification (suspected PICs @mentioned) → (4) shown in this page's unrecognized pool together with the tracking number and suspected orders ("contains the product + Processing" condition, multiple possible) → (5) the responsible PIC reviews & matches via "Review & Match" (M1) → removed from the pool + the registrant is @mentioned via a comment automatically posted to the order's Comments. See the View Orders wireframe for the registration popup mock. (Confirmed 2026-08-02) Unrequested inbound shipments also use this pool — when the invoice scan of arrived stock matches neither a customer order nor an inbound request, it is sent to unrecognized the same way. After the owner creates an inbound request, enters the invoice number, and removes the row from the pool (✕ → removal confirm modal M2, reason "Routed to inbound request" + Inbound No. — 2026-08-03), rescanning enters the View Orders internal-inbound screen (State 6) normally. Leaving a "suspected inbound stock" note in the registration memo speeds up routing to the owner.
